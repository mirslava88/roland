# Восстановление захвата виртуальной камеры

## Наблюдение и границы диагноза

Пользователь сообщил: сначала виртуальная камера работала, затем после выхода
из эфира Сцены изображение стало чёрным. В работающем приложении подтверждено:
физический Program-дисплей содержит изображение, камера имеет статус `running`
и источник `display`, но счётчик и время записи её общей памяти не меняются.
Установленная source DLL совпадает с локальной сборкой.

В прежнем `DisplayCapture::Capture` восстановление после `DXGI_ERROR_ACCESS_LOST`
выполнялось ровно один раз. Если `DuplicateOutput` в этот момент не удавался,
все следующие вызовы сразу возвращались из-за пустого объекта duplication.
Другие ошибки DXGI также не запускали восстановление. Точный исходный HRESULT
живого зависания неизвестен: прежний host его не журналировал.

## Исправление

- Неудачная попытка восстановления больше не обрывает дальнейшие попытки:
  DXGI/D3D пересоздаются с ограничением частоты, раз в 500 мс.
- Ошибки получения, копирования и освобождения кадра инвалидируют захват.
  Отсутствие первого кадра более 3 секунд запускает повторную инициализацию.
  Неизменный рабочий стол после первого кадра остаётся нормальным случаем.
- Старый кадр не подтверждает новый физический маршрут. Виртуальное устройство
  остаётся прежним, без Stop/Start в приложении видеосвязи.
- Host сообщает начало и завершение восстановления; основной процесс принимает
  только сообщения текущего host/маршрута/requestId. Повторное уведомление при
  затянувшемся восстановлении покрывает окно запуска подписчика. Настройки
  показывают восстановление жёлтым, вместо обещания доступного изображения.
- Начальный requestId передаётся host при запуске, в том числе после Stop/Start.
  Запись JSON-уведомлений из разных потоков сериализована.
- Масштабирование, пропорции, ориентация, source DLL и отсутствие передачи звука
  не менялись. Захват не возвращается к GDI/CAPTUREBLT.

## Воспроизводимые проверки

`PDMVirtualCameraHost.exe --test-display-recovery --x X --y Y --width W --height H`
проверяет настоящий DXGI-захват с искусственной инвалидацией access lost,
device removed и access denied, неудачной первой попыткой на отсутствующем
экране, ограничением частоты повторов и последующим восстановлением кадров.
Тест не создаёт камеру и не пишет в её общую память.

`node scripts/test-race-regressions.cjs` включает проверку уведомлений
восстановления, устаревших requestId, замены host и перехода на внутренний эфир.

`node scripts/test-live-scene-presentation-switch.mjs --physical-camera true --exit-scene true --probe-camera true --cycles 4`
на тестовом стенде с готовыми PPTX/PDF-каналами включает и выключает Сцену
реальными кнопками, затем выводит канал. Получатель DirectShow читает кадры
виртуальной камеры. Проверяется обновление общей памяти, ненулевое изображение
у получателя и неизменность host между переключениями. Вспомогательный
`test-virtual-camera-live-frame.ps1` только читает согласованные статистики
кадра и не сохраняет содержимое изображения.

Это проверка локального получателя Windows, не удалённого клиента ВКС.
Искусственная инвалидация DXGI не является физическим отключением HDMI.

Результаты: нативный recovery-тест прошёл на дисплеях 1920×1080 и 1920×1200;
18/18 проверок гонок и полный `test-critical.mjs all` — 25/25 за 297 секунд,
включая строгие типы, обе сборки, Scene/обучение UI и streaming. В синтетическом
Scene UI остаются прежние сообщения `setPointerCapture` для искусственных
указателей; все assertions группы прошли.

На свежезапущенной финальной сборке повторно прошли 4 цикла выхода из Сцены
и TAKE PDF/PPTX: DirectShow получал не-чёрные кадры, shared-frame sequence
продолжал расти, host оставался прежним. Runtime-smoke подтвердил открытое
операторское окно, камеру `running` и выключенный режим Сцены.
